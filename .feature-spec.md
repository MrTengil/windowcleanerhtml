# Vertical Shine — Window Cleaner Game

## Concept

A mobile-style window cleaning game. You clean windows covered in dust, grime,
bird poop, boarded-up screws, police tape, etc. Different dirt types are
removed with different interactions (tap, press & hold, press & rotate,
scratch) using different tools, each with its own on-screen animation. When a
window is fully clean, you move to the next floor.

House types (different heights/challenges, different lift devices):
- Brick houses (tap interaction, e.g. squeegee, gondola lift)
- Modern NYC glass-facade towers (press & hold, e.g. pressure washer, scissor lift)
- Worn-down apartments (press & rotate on screws, crane)
- Cathedrals (scratch, e.g. scraper, crane)

Design reference mockup: `image.png` ("Vertical Shine" — main menu/location
select, per-house-type clean screens, tool modifications screen, level
complete screen).

Everything should be data-driven/modular so house types, dirt types, tools,
and lifts can be swapped in and out without touching core game code.

## Phase 1 scope (this branch)

Goal: prove out the modular architecture end-to-end with **one fully
playable house type**, reachable from a real main menu, per the spec's
explicit ask: "We need a main screen to decide what house we're working on
to try it out."

**Tech stack:** Phaser 3, loaded via CDN `<script>` tag (no bundler/build
step). Game code as plain ES modules under `src/`, data-driven config for
houses/dirt/tools/lifts. Portrait design resolution, scaled with Phaser's
`Scale.FIT`.

**Visuals:** No real art assets in this phase. Placeholder graphics only —
flat-colored rectangles/shapes and text drawn via Phaser's Graphics/Text
APIs, loosely matching the mockup's layout and color language.

### In scope

1. **Main Menu / Location Select screen** (`MainMenuScene`)
   - Title "Vertical Shine"
   - 4 house cards: Brick Town, Glass Towers, Worn District, Saint's
     Cathedral — each showing name, floor count, difficulty, placeholder
     color/icon, per the mockup
   - Only **Brick Town** is enabled/tappable; the other three render in a
     dimmed "coming soon" state (no navigation) — establishes the roadmap
     without building them yet
   - Toolbelt panel (Scraper, Squeegee, Screwdriver, Pressure Washer) —
     display-only placeholders in this phase
   - Lift Garage panel (Gondola, Scissor Lift, Crane) — display-only
     placeholders in this phase
   - Tapping Brick Town transitions to `HouseCleanScene` configured for the
     brick house

2. **House Clean scene** (`HouseCleanScene` — generic, data-driven, instanced
   for Brick House in this phase)
   - Brick house config: 5 floors (shortened from the mockup's 12 for faster
     playtesting), each floor is one window with a handful of dirt spots
     (dust + bird poop), all using the **tap** interaction
   - HUD: floor counter ("Floor X/5"), progress bar, pause button (button
     can be a non-functional stub)
   - Gondola placeholder rendered at the bottom of the window — decorative
     only in this phase, no independent movement control
   - Squeegee tool auto-equipped (single tool/interaction type, so no
     toolbelt switching logic needed yet)
   - Tap interaction: tapping a dirt spot decrements its remaining hits,
     plays a brief scale/fade hit animation; spot is removed once hits reach
     0; when all spots on a window are clear, play a short "floor clear"
     beat, then advance to the next floor with newly spawned dirt spots;
     after the final floor, show a simple placeholder "Level Complete"
     overlay with a button back to the Main Menu

### Modular architecture (data/config layer)

- `src/config/houses.js` — house definitions: id, name, floor count,
  difficulty, lift type, dirt types that can appear, placeholder
  background/colors
- `src/config/dirtTypes.js` — dirt/grime definitions: id, interaction type
  (only `tap` implemented this phase; others reserved), tool required,
  placeholder shape/color, hits-to-clean
- `src/config/tools.js` — tool definitions: id, name, placeholder
  icon/color, compatible dirt types
- `src/config/lifts.js` — lift definitions per house type (visual only this
  phase)
- Scenes read this config and procedurally spawn windows/dirt
  spots/lift/HUD rather than hardcoding Brick House — this is what makes
  adding the other 3 house types later a config change, not a rewrite
- `src/interactions/` holds one module per interaction type. Only
  `TapInteraction.js` is wired up this phase; the folder structure reserves
  room for `PressHoldInteraction.js`, `PressRotateInteraction.js`, and
  `ScratchInteraction.js` to be added later without touching core
  scene/entity code

```
  css/style.css               # page/canvas centering
  src/

    config/
      houses.js
      dirtTypes.js
      tools.js
      lifts.js
    scenes/
      BootScene.js             # generates placeholder textures, boots to menu
      MainMenuScene.js
      HouseCleanScene.js
    entities/

```

## Revision 3 plan

Continues on this branch, same as prior revisions.

1. **Fix the progress-bar accuracy bug.** Root cause: `HouseCleanScene`'s
   `markRevealedUnderBrush` marks a fixed 3x3 grid of sample points spaced
   out to the brush radius around every swipe-path point. Combined with
   grid-cell quantization (a single marked point reveals its *whole* 40px
   cell), this measurably over-counts — the screenshots show the bar at
   ~50%/~90% when the visibly-scratched area looks closer to ~15%/~65%.
   Fix: replace it with a proper circle-vs-cell intersection test —
   `RevealTracker.markRevealedInRadius(x, y, radius)`, a new method that
   marks exactly the cells whose center falls within `radius` of the given
   point (bounds-checked so off-grid cells near the window edge are never
   counted). Strict TDD. `HouseCleanScene` calls this once per interpolated
   swipe point instead of the old hand-rolled sampling.

2. **Raise the completion threshold from 90% to 99%**, per your note —
   verified empirically after the accuracy fix (a thorough sweep should
   still reach it without feeling impossible).

3. **Full building-height feature** (ground at floor 1, roofline at the
   top floor), per your choice of the deeper option:
   - The wall becomes a single edge-to-edge rectangle covering the *entire*
     canvas (`house.color`) — this alone fixes the "floating card" look,
     since there's no gap on any side ever.
   - A **ground strip** (bottom of the screen) is visible only when
     `currentFloor === 1`.
   - A **roof/sky strip** (top of the screen, flat sky-blue) is visible
     only when `currentFloor === house.floors`.
   - Both are toggled together by one `updateBuildingState()` call inside
     `resetFloor()` (so it runs on initial load and after every floor
     transition) — no continuous world-scroll/camera model, since ground
     and roof only ever matter at the two endpoints and every floor
     in between is indistinguishable plain wall. This keeps the feature
     genuinely tied to floor state (not just cosmetic) without the
     complexity/scaling problems of a literal per-floor scrolling
     building height.
   - The standalone full-canvas sky gradient is removed — since the wall
     now always covers the whole screen, that layer was never actually
     visible; its color lives on as the roof strip's flat sky-blue fill.

Out of scope (unchanged): wall/ground/roof do not animate/slide during the
floor transition (they snap at the same moment the window content is fully
faded out, same treatment as the floor-counter text), toolbelt switching,
Level Complete scoring, upgrade screen, currency/persistence, real
art/audio.

## Revision 9 plan

Continues on `main` (now the active line of work).

**Root cause of why it still looks wrong:** the window slides only 150px
(`FLOOR_TRANSITION_OFFSET`) — barely a quarter of its own 560px height —
and the wall behind it never moves at all. The wall is the only element
that conveys vertical position, so with it static there is no positional
cue that you climbed anything; it reads as a card shuffling in place. Two
independent per-container tweens also mean "where everything is" is
implicit rather than derived from one source of truth.

**Replace both tweens with a single world-scroll offset**, per your
description:

1. **One scalar drives everything.** `this.scroll = { offset: 0 }` —
   a plain object so it can be tweened. Advancing a floor tweens
   `offset += SEGMENT_SPACING`; nothing else is animated directly.

2. **Segments live at fixed world positions.** Floor N's segment gets
   `worldY = WINDOW_Y - (N - 1) * SEGMENT_SPACING`, assigned once at
   construction and never mutated. Floor 1 sits at 460, floor 2 at -308,
   floor 3 at -1076, and so on — the building exists in world space and
   the player climbs through it.

3. **The offset is applied every frame in `update()`** (the camera/player
   never moves):
   - `segment.container.y = segment.worldY + this.scroll.offset` for every
     active segment
   - `this.wall.tilePositionY = -this.scroll.offset` — the wall stays one
     `tileSprite` but its *texture* scrolls, so the brick courses, quoins
     and drainpipe visibly travel past. This is what sells the infinite
     building, and it costs no extra objects.

   Because both come off the same number, segments and wall cannot drift
   out of sync — the failure mode is structurally gone rather than
   something to keep re-verifying.

4. **`SEGMENT_SPACING = 768`** (two 384px wall tiles), per your answer.
   A multiple of 384 keeps the wall's quoin/brick phase identical at every
   floor, so each floor's resting frame looks the same. At 768 the
   previous floor's window stays partly visible at the bottom of the
   screen and the next waits just off the top — a continuous building
   rather than isolated cards. Duration goes 350ms → ~700ms, since we now
   travel 5x further and want it to read as a deliberate climb.

5. **Segment lifecycle.** `this.segments` holds `{ container, dirtMask,
   worldY, floor }`. Advancing spawns the next floor's segment (which is
   automatically off-screen above by virtue of its `worldY`), repoints the
   active dirt mask at it, resets it, then tweens the offset. Once the
   tween finishes, any segment that has scrolled a full spacing past the
   canvas bottom is destroyed. That keeps ~3 alive at a time — enough for
   the peek, bounded regardless of how many floors a house has.

6. **Ground/roof are unchanged** — they remain local children of their own
   floor's segment (from Revision 8), so they inherit the segment's
   transform for free, which is exactly the "anchored features defined in
   the segment's local space" model.

**Invariant worth stating explicitly:** `toWindowLocal()` and
`isInsideWindow()` convert pointer coordinates using fixed
`WINDOW_X`/`WINDOW_Y` constants, which are only correct while the active
segment is at its resting position. That holds because input stays blocked
for the whole scroll via `isTransitioning` — so this keeps working, but the
two are now coupled and the coupling is easy to break silently.

Out of scope: the scroll is still driven by floor completion (one tweened
offset change per floor), not by continuous free movement. Toolbelt
switching, Level Complete scoring, upgrade screen, currency/persistence,
and art for the other houses/tools remain deferred.
